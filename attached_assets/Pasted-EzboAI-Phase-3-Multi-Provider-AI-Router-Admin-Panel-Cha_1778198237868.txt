EzboAI Phase 3 — Multi-Provider AI Router + Admin Panel + Chat Backend
What & Why
This is the brain of EzboAI. Build a backend AI Router that supports 6 AI providers (OpenAI, OpenRouter, Anthropic Claude, xAI Grok, Replicate, Google Gemini), with API keys supplied by the user via a password-protected Admin Panel at /admin. The router picks the right provider+model per task type (chat-fast / chat-smart / vision / code / image-gen / audio / web-agent / embedding) and falls back automatically when one fails. Chat replies stream into the Phase 2 UI via Server-Sent Events.

The user explicitly does NOT want to use Replit's AI Integration proxy — they will plug in their own keys. The admin panel must let them add/test/enable/disable keys per provider, choose which models from each provider are usable, and configure a fallback chain.

New DB tables (Drizzle):

provider_usage (id, provider, model, taskType, inputTokens, outputTokens, latencyMs, costUsd, error, createdAt)

New API routes:
POST /api/admin/login — body {password}, sets HTTP-only cookie if matches ADMIN_PASSWORD
POST /api/admin/logout
GET /api/admin/me — returns {loggedIn: bool}
GET /api/admin/providers — list (masked keys)
POST /api/admin/providers — {provider, label, apiKey} add/update
DELETE /api/admin/providers/:id
PATCH /api/admin/providers/:id — {enabled, label}
POST /api/admin/providers/:id/test — calls provider's testConnection; updates lastTestedAt, returns result
GET /api/admin/providers/:id/models — fetches live model list
GET /api/admin/routing-rules / PUT /api/admin/routing-rules — manage routing config
GET /api/admin/usage — returns aggregated usage by day/provider/task
POST /api/chat/stream — SSE: {messages, threadId?, modelOverride?}, calls router, streams chunks
All admin routes protected by middleware checking the admin session cookie.
All API key fields encrypted at rest using APP_ENCRYPTION_KEY env var (32 bytes, AES-256-GCM with random IV per row).
Frontend never receives the raw key — only masked form like sk-...XXXX (last 4 chars).

Acceptance criteria

Add an OpenAI key → "Test" → green check.
Add a Claude key → "Test" → green check.

Steps
Read skills — environment-secrets (to set ADMIN_PASSWORD, APP_ENCRYPTION_KEY, SESSION_SECRET), database (Drizzle schema push).
Set required env vars — Use the environment-secrets skill to create ADMIN_PASSWORD, APP_ENCRYPTION_KEY (32 random bytes base64), SESSION_SECRET. Do not set any AI provider keys as env vars.
Install deps in api-server — openai, @anthropic-ai/sdk, @google/genai, replicate, cookie-parser, express-session (or simple cookie auth), zod (validation).
Drizzle schema — Add provider_keys, routing_rules, provider_usage, admin_sessions tables in artifacts/api-server/src/db/schema.ts. Run drizzle-kit push.
Crypto utility — src/ai/crypto.ts with encrypt(plaintext) returning {ciphertext, iv, authTag} joined as a single string; decrypt(stored) reverses. Use crypto.createCipheriv('aes-256-gcm', key, iv).
Provider adapter interface — src/ai/providers/types.ts defines the unified interface every provider implements.
Implement each provider adapter:
openai.ts — uses openai SDK; supports chat (streaming), vision, listModels, testConnection (calls models.list())

replicate.ts — uses replicate SDK; mainly for image-gen, audio; chat support optional via Llama models

Critical constraints / Security
API keys MUST be encrypted at rest. Never log raw keys. Never include raw keys in API responses (always mask).
Admin password stored only in env var, never in DB; compare with crypto.timingSafeEqual to prevent timing attacks.
Session cookies must be HTTP-only, Secure (in production), SameSite=Lax.
Rate-limit /api/admin/login to prevent brute-force (e.g. 5 attempts per 15 min per IP).
All admin routes require valid session.
The chat stream endpoint should NOT require admin auth (chat is for end users); but it requires at least one configured provider, otherwise returns a clean error.
Validate all user inputs with zod before touching DB or providers.
